# Architecture

```
src/
  PdfViewerLite.Core            UI-agnostic model: documents, layout, render scheduling, tile cache, search, settings
  PdfViewerLite.Pdfium          PDFium bindings and the IDocumentEngine implementation
  PdfViewerLite.Platform.Linux  D-Bus single instance, FileManager1, kdeglobals, recently-used.xbel
  PdfViewerLite.Http            Refit clients (update checks, remote documents)
  PdfViewerLite.App             Avalonia + ReactiveUI application
tests/                          TUnit tests, including headless UI tests
benchmarks/                     BenchmarkDotNet allocation and throughput benchmarks
packaging/linux/                Desktop entry, AppStream metadata, icon, AppImage, nfpm (deb/rpm) and AUR recipes
```

## Documents

`IDocumentEngine` opens an `IDocument`; `PdfiumEngine` is the only engine today, and others (comics, TIFF) can be
added behind the same interface. Documents report geometry in unrotated *page space*: points, top-left origin, Y
down. PDFium's own coordinates are converted through a virtual device (`FPDF_PageToDevice`) so crop boxes and
intrinsic `/Rotate` are honoured.

PDFium is not thread safe, so every native call runs under one process-wide lock (`PdfiumLibrary.EnterScope`).
Loaded pages and text pages are cached per document (8 pages) so tiles of the same page don't re-parse it. Native
handles are `SafeHandle`s, and `unsigned long` parameters use `CULong` because its width differs between Windows and
Unix.

A tab holds a `DocumentSource`, not a document. The `DocumentPool` opens documents on demand and closes the least
recently used ones beyond its capacity (16 by default), keeping page sizes, outline and metadata so closed documents
can still be laid out. This is what makes hundreds of tabs cheap.

## Rendering pipeline

1. `PageCanvas` (inside a `ScrollViewer`) asks `DocumentLayout` which pages intersect the viewport, a binary search
   over row offsets.
2. For each visible page it draws the low-resolution preview (220px wide, shared with sidebar thumbnails), then the
   full-resolution 512px tiles for the current scale. Tile origins are snapped to device pixels so there are no seams.
3. Missing tiles are requested from the `RenderScheduler` with the canvas's `RenderClient` generation, which advances
   every frame. A queued request whose generation is no longer current is dropped before PDFium sees it, so
   scrolling quickly never builds a backlog.
4. The scheduler's single render thread takes requests by priority (visible previews, visible tiles, prefetch,
   thumbnails, background) and renders straight into an Avalonia `WriteableBitmap` through `IRenderSurface`. The
   tab's `PageTone` (paper and ink colours) is applied in place through a per-channel lookup table.
5. The scheduler's `Completed` observable emits once per batch; `RenderHub` observes it on the main thread
   sequencer, moves the tiles into the `TileCache` (an LRU bounded by bytes, 256 MB by default) and emits
   `TilesArrived`, which visible canvases and thumbnails subscribe to.

The render path allocates no managed memory per tile; see the benchmarks.

## Notifications

There are no .NET events in the codebase's APIs. Everything that notifies is an `IObservable<T>` built on
ReactiveUI.Primitives: render completion, tile arrival, navigation and link requests, search highlight changes,
file changes (`FileChanges.Watch`, a cold observable that owns a `FileSystemWatcher` while subscribed), the desktop
palette (current value then changes) and D-Bus open requests. Views observe view model properties with
`WhenAnyValue`, Avalonia properties and routed events with `GetObservable`, and dispose subscriptions through
`MultipleDisposable`.

## Application

View models are ReactiveUI `ReactiveObject`s with `ReactiveCommand`s; property observation (`WhenAnyValue`) is
source-generated by ReactiveUI.Binding, so it is AOT safe. Views are plain Avalonia windows and user controls with
compiled XAML bindings. `ReactiveWindow` activation is not used because ReactiveUI.Avalonia marks it
`RequiresUnreferencedCode`. Dialogs go through ReactiveUI `Interaction`s handled by the window.

`AppServices` is the composition root. `ThemeResolver` combines the comfort settings with the desktop palette
(`IDesktopThemeSource`) into a `ResolvedTheme`. `AppServices.Theme` republishes it, and `DesktopThemeApplier` writes
it into application resources and the Fluent palette, so KWin's server-side decorations and the window content
match. See [COMFORT.md](COMFORT.md).

## Single instance and Dolphin

The first process owns `net.glennwatson.PdfViewerLite` on the session bus and serves `org.freedesktop.Application`
(`Open`, `Activate`). Later launches, such as Dolphin running `pdfviewerlite %U`, call `Open` with absolute paths
and the launcher's activation token, then exit. `--new-instance` skips this. The desktop file id, D-Bus name and
`StartupWMClass` share the application id so Plasma associates windows with the launcher.
